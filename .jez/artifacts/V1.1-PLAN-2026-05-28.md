# Office Town v1.1 — Plan

Builds on the v1.0 shipped state (single Worker + 3 MCP gateways + Goose plugin + template + 8 knowledge files). v1.1 adds the **rich-media + sync + sandbox + declarative-extension** layer that takes Office Town from "wiki + agent roles" to "the agent fleet's complete capability surface."

Four phases, sequenced by foundation → polish → richness → advanced. Each phase shippable independently.

## Phase 1 — Foundation gaps (~1 week)

The bits we should have shipped in v1.0 but didn't. Highest priority.

### 1.1 Restore browser rendering (Option B per Jez's reply)

**Why**: Removing `office-town-browser` left a real gap — agents can't scrape JS-rendered pages without installing external Playwright or pack-cloudflare. For SPAs / modern web, no JS = blank shell.

**Shape**: Re-add Browser Rendering binding (`browser: { binding: BROWSER }`) + add `fetch_with_js` action to files MCP gateway (cleaner than separate `/mcp/browser`). One tool call: URL → puppeteer render → toMarkdown → return.

```typescript
files(action: 'fetch_with_js', url: 'https://...', wait_for_selector?: string,
      viewport_width?: number, save_to_files?: string)
// Returns { url, title, markdown, screenshot_base64?, size_bytes }
```

Plus a `screenshot` action:
```typescript
files(action: 'screenshot', url: '...', full_page?: boolean, save_to_files?: string)
```

**Effort**: 1 hour. Restore puppeteer dep + binding + 2 actions.

### 1.2 MCP Sampling synthesis on wiki.search

**Why**: `wiki(action: 'search', synthesize: true)` currently returns `{hits, synthesized: null}` — synthesis is stubbed not implemented. Per MEMORY-COMPARISON.md design contract #7: use MCP Sampling to ask the host LLM for a synthesised answer from top hits (zero cost added since it's the user's own LLM bill).

**Shape**: When `synthesize: true`, the MCP server sends a `sampling/createMessage` request back to Goose with the top-N hits + the query, asks for a summary, returns synthesis + citations.

**Effort**: 4 hours. New `sampling.ts` helper, wired into wiki MCP search handler. Per goose-knowledge-04 the contract is well-documented.

### 1.3 Cron MCP wrapper

**Why**: Cron is currently HTTP-only (`/api/cron/*`). Agents would have to use a generic HTTP-call tool to schedule recurring routines. Wrapping in MCP makes the librarian/scout's "schedule weekly news sweep" trivial.

**Shape**: Add `office-town-cron` to the worker — single gateway tool `cron` with actions: `schedule, list, get, run_now, history, delete, pause, resume`.

**Effort**: 4 hours. Same gateway-pattern shape as wiki/files/email. Reuses existing CronService.

### 1.4 office-town-pack-cloudflare plugin

**Why**: We dropped our `office-town-devops` MCP per scope-audit, deferring to Cloudflare's official MCPs at `github.com/cloudflare/mcp`. But users have to install those manually. A pack-cloudflare plugin bundles them + bundles Cloudflare's official skills (`github.com/cloudflare/skills`) in one `goose plugin install`.

**Shape**: New repo `jezweb/office-town-pack-cloudflare`. Open Plugin Spec — `.plugin/plugin.json` declares: skills from cloudflare/skills, MCP server install commands for cloudflare/mcp servers (workers-bindings, dns, r2, d1, observability), plus an OT-specific README explaining when to use which.

**Effort**: 1 day. Mostly assembly + documentation.

**Phase 1 total: ~1 week. Ships browser rendering, synthesis, cron MCP, and a real Cloudflare-ops install.**

## Phase 2 — Sync + declarative extensions (~2 weeks)

### 2.1 officetowd — Go-lang sync daemon

**Spec**: Full spec at `.jez/artifacts/officetowd-spec-2026-05-28.md` — already written.

**Why**: Per Jez 2026-05-28 — Syncthing too slow, rclone-mount too fragile. Build the proper Goanna-style daemon. v1.1 differentiator: "your wiki, on every machine, in your IDE/editor too."

**Shape**:
- Single Go binary, cross-platform (macOS + Linux + Windows)
- fsnotify watcher + SQLite manifest + AWS S3 SDK for R2
- Bisync algorithm with conflict resolution
- CLI: `officetowd {start, stop, status, logs, configure, resync, push, pull}`
- Distribution: Homebrew tap (`brew install jezweb/tap/officetowd`)
- Webhook to worker on file change → triggers re-index

**Effort**: ~1-2 weeks. Per the spec: 2d fsnotify+manifest, 2d R2 client, 3d bisync algorithm, 2d CLI+config, 1d brew formula, 1d worker integration, 2d cross-platform testing.

**Repo to create**: `jezweb/officetowd`.

### 2.2 ~~Declarative extension JSONs upstream~~ → Deeplinks on landing + dashboard

**Pivot**: My earlier plan was wrong — Goose doesn't have a declarative HTTP-MCP registry analogous to the provider JSONs (the Alibaba PR pattern only covers providers). The equivalent for HTTP MCPs is **Goose deeplinks**: `goose://extension?name=...&type=streamable_http&url=...&header=Authorization=Bearer%20XXX&description=...` URLs that, when clicked, pop up Goose's "Add Extension" dialog pre-filled.

**Shape**: Add deeplink buttons to:
- `officetown.au` landing page — three "Add to Goose" buttons (one per MCP) that the user clicks AFTER deploying their backend (URL+token come from the user's deployment)
- The deployed worker's dashboard — same buttons, pre-filled with the user's URL+token from their deploy

The dashboard generates the deeplinks server-side using the user's actual deployment URL + their bearer token (already known to the worker), so the user just clicks once per MCP.

**Effort**: ~3 hours total. Way faster than upstream PRs + better UX (no Goose release needed).

### 2.3 AI Search benchmark spike

**Why**: Cloudflare AI Search (released April 2026, free in beta) overlaps with our wiki search backend (FTS5 + Vectorize + RRF). Could be better, could be worse. Per cloudflare-knowledge-02: embedding model is fixed at instance creation (lock-in concern), but quality might be worth it.

**Shape**: Spike that:
1. Deploys an AI Search instance against the same wiki content
2. Runs ~50 representative queries against both backends
3. Compares: quality (judge model), latency, cost
4. Decision: swap, hybrid, or keep DIY

**Effort**: 1 day. Don't commit to switching; learn whether it's worth it.

**Phase 2 total: ~2-3 weeks. Ships the sync daemon (big differentiator) + makes Office Town first-class in Goose's extension picker.**

## Phase 3 — Rich media + sandbox (~2-3 weeks)

### 3.1 Voice MCP — Workers AI STT/TTS today, Realtime Agents for v1.2

**Status (2026-05-28 verification)**: Cloudflare ships `@cloudflare/voice` and `@cloudflare/realtime-agents` packages — the AI bot runs inside a Durable Object and joins a RealtimeKit meeting natively. The earlier claim that "Workers can't hold WebRTC peers" was wrong — verified against `developers.cloudflare.com/realtime/agents/getting-started/`.

**Shipped in v1.1** (works today via Workers AI direct):
- `transcribe` — Nova-3 binding (`env.AI.run('@cf/deepgram/nova-3', ...)`)
- `synthesize` — Aura-2 binding with 40 voices
- `list_voices` — voice catalog

**Stubbed for v1.2** (needs Durable Object + dashboard widget):
- `call_create` / `call_end` / `call_status`
- New DO class extending `RealtimeAgent` from `@cloudflare/realtime-agents`
- Pipeline: `[RealtimeKitTransport, WorkersAINova3STT, textProcessor, WorkersAITTS, RealtimeKitTransport]`
- Browser side: standard RealtimeKit Web SDK in a new `/dashboard/call/<id>` page
- Each deployer needs a Cloudflare Realtime app ID + secret (one-time setup)

**v1.2 effort**: 1-2 days for the DO + dashboard widget + RealtimeKit credential plumbing.

### 3.2 Sandbox MCP — Cloudflare Containers

**Why**: Agents need to run arbitrary code (Python for data analysis, Node for transformations, etc.). Cloudflare Containers gives sandboxed code execution.

**Shape**: New MCP `office-town-sandbox` at `/mcp/sandbox`. Gateway tool `sandbox` with actions:
- `run` — execute code in a fresh container, return stdout+stderr
- `install` — pip/npm install before run
- `persist_session` — keep a container warm for follow-up calls
- `kill_session` — stop a persistent container

Default languages: Python 3.12, Node 22, Bash. Time/memory limits enforced.

**Effort**: 1-2 days. Containers SDK + lifecycle management.

### 3.3 Image generation action

**Why**: Designer/worker role needs to generate images (mockups, social posts, illustrations). Workers AI FLUX 2 Klein / FLUX 2 Dev for generation.

**Shape**: Add `generate_image` action to files MCP gateway:
```typescript
files(action: 'generate_image', prompt: '...', width?, height?, aspect_ratio?,
      style?, save_to_files?: string)
// Returns { saved_to?: string, image_base64?: string, size_bytes }
```

**Effort**: 3 hours. Reuses files MCP's I/O patterns; just adds the env.AI.run() call to FLUX 2.

### 3.4 TTS action (text → audio)

**Why**: Pair with voice MCP. Agent generates audio narration / podcast snippets / notification chimes.

**Shape**: Add `speak` action to files MCP gateway:
```typescript
files(action: 'speak', text: string, voice?: string, save_to_files?: string)
// Returns { saved_to?: string, audio_base64?: string, size_bytes, voice }
```

Uses Workers AI Aura-2 binding.

**Effort**: 3 hours.

**Phase 3 total: ~2-3 weeks. Office Town agents can now generate/transform every media type.**

## Phase 4 — Advanced (deferred, no specific deadline)

### 4.1 MCP Apps — dashboard embedded in Goose

**Why**: Currently the dashboard lives at `/dashboard` on the worker's URL — a separate browser tab. With MCP Apps + MCP-UI (per goose-knowledge-04 §2), the dashboard becomes an embedded iframe inside Goose Desktop. User doesn't context-switch.

**Shape**: Add `_meta.ui` block to wiki MCP's `tools/list` response. Returns a `ui://office-town-dashboard` resource that Goose Desktop renders inline.

**Effort**: 1-2 days. Pattern is documented; main work is making the dashboard responsive to MCP App size constraints.

### 4.2 Workflows for heavy operations

**Why**: Worker requests cap at ~30 seconds. For tasks like "ingest 100 PDFs into the wiki" or "rebuild the embedding index", Cloudflare Workflows lets us hibernate between steps and survive >30 min runtimes.

**Shape**: New `src/workflows/` directory. Two initial workflows:
- `bulk_ingest` — N files → toMarkdown → wiki.create
- `reindex_all` — for embedding model upgrades

**Effort**: 1 day. Workflows SDK is well-trodden.

### 4.3 Stream MCP — video

**Why**: Video upload, transcoding, captioning. v2 candidate.

### 4.4 Knowledge Graph integration

**Why**: Multi-hop relational reasoning over the wiki. Per office-town.md original design, this was a separate npm extension users opt into. We could integrate (auto-extract entities from wiki entries, build graph, expose via wiki.related).

**Effort**: 2-3 days exploration. Deferred until we see real demand.

## Cross-cutting: what stays the same

- **Single Worker + single substrate bucket** (no splitting)
- **Gateway-pattern MCP tools** (one tool per server, multiple actions)
- **`why:` required on every mutation**
- **Bindings over API keys** wherever possible
- **Open Plugin Spec** for distribution
- **Master plan §2 architectural decisions** stay locked

## Sequencing recommendation

Ship Phase 1 first (1 week) — fixes real v1.0 gaps. Then Phase 2's officetowd (1-2 weeks) — biggest differentiator. Then Phase 2's declarative PRs in parallel with Phase 3. Phase 4 items deferred until specific demand.

Total v1.1: **~5-6 weeks** of focused work to ship Phases 1+2+3. Phase 4 stays on the v2 horizon.

## Risk register

| Risk | Mitigation |
|---|---|
| Goose's `goose mcp add` CLI doesn't exist or differs from docs | Phase 1.1+ tests this on real Goose install. Falls back to documenting deeplink format. |
| Cloudflare Containers GA status / pricing changes | Sandbox MCP design defers to it. If pricing shifts, swap to Workers AI sandboxes or external service. |
| Workers AI Aura-2 / Nova-3 deprecate | Voice MCP uses Workers AI bindings — provider swap is straightforward. |
| Declarative extension JSON PRs sit unmerged in Goose upstream | Ship `goose mcp add` flow as the canonical install path; declarative PRs are polish, not critical. |
| officetowd cross-platform sync conflicts | Bisync algorithm includes conflict-keep-both. Worst case = duplicate files locally, agent sees both. |

## What's NOT in v1.1

- Custom Goose distribution (parked permanently per conversation-audit)
- Multi-tenant SaaS (per-deployment infrastructure stays the model)
- Mobile apps (Goose mobile is the path)
- AI Gateway (deferred until Cloudflare fixes the streaming multibyte bug per cloudflare-workers.md rule)
- Cron MCP that runs in remote `goosed` (the current cron MCP triggers Worker cron handlers; remote goosed is v2)

## Decision needed before Phase 1 starts

1. **Browser rendering shape**: confirm Option B (add to files MCP) vs Option A (restore as separate office-town-browser MCP). My recommendation: B.
2. **Phase order**: 1→2→3, or 1→3→2 (deliver voice/sandbox before sync daemon)? Sync daemon is bigger differentiator; recommend default 1→2→3.
3. **Should we contribute the declarative extension JSONs in one PR or three?** One PR keeps reviewer context fresh; three lets each merge independently. Recommendation: one PR, three files.

Once these are answered, Phase 1 can start immediately.
